# Архитектура MD2DOC Converter 0.2.3

## Поток данных

```text
CLI / Studio (FastAPI + SvelteKit)
  → core.builder.build_project
  → config.loader: адаптер общего пакетного Validator 0.1/0.2
  → core.project_loader: проверенные конфигурации и sources
  → core.markdown_parser: markdown-it → независимые Block/Inline
  → core.structure_builder: дерево Element и таблица целей
  → core.numbering (0.1) / core.heading_numbering (0.2): план номеров
  → core.style_resolver: итоговое оформление
  → renderers.docx_renderer: python-docx + изолированные OOXML extensions
  → renderers.integrity: ZIP/OPC/XML/стили/закладки/связи/списки/reopen
  → атомарная публикация DOCX + JSON-отчёт
```

## Загрузка и валидация

`config.loader` импортирует `md2doc.config.validation` из установленного пакета.
Класс-адаптер переводит `error/warn` в структурированные Diagnostic. Правила
0.1 перенесены из исторического валидатора; его проектная копия не менялась и
не является зависимостью. Новые поля проверяет config.heading_numbering. Проверяются
также выключенные sources. После успешной проверки удаляются игнорируемые
`x-*` поля, не меняя входные файлы. YAML читается тем же загрузчиком, включая
контроль повторных ключей и запрет тегов/алиасов/якорей.

Входные проекты не предоставляют исполняемый код. MD2DOC_VALIDATOR игнорируется;
для wheel/EXE все входные проверки поставляются в том же пакете.

## Модель документа

`DocumentModel` содержит конфигурации, дерево элементов и карту навигационных
целей. `Element` хранит id, тип, физический путь source, body-стиль, блоки,
структурный номер, стиль собственного заголовка, запросы разрывов и детей.
`Block` — заголовок, абзац, контейнер, список, таблица, код и т. п.; `Inline` —
типизированные токены текста, выделения, ссылок, кода и изображений.
Модель не содержит объектов python-docx и пригодна для другого рендерера.

Обход — preorder, строго по массивам манифеста. Выключение родителя исключает
всё поддерево. Заголовок `from: markdown` использует первый существующий AST
heading; `from: yaml` добавляет один текстовый heading перед содержанием.
Подстановка metadata выполняется **после** синтаксического разбора в текстовых
токенах. Код и подписи изображений не интерполируются. Значение metadata не
может создать Markdown-разметку или новый блок.

Специальные контейнеры и pagebreak реализованы двумя узкими блоковыми правилами
markdown-it. Основной Markdown разбирается библиотекой, не regexp-конвертером.
Регулярные выражения применяются только к маркерам расширения, шаблонам и
совместимому вычислению slug.

## Структура и нумерация

В схеме 0.1 независимые счётчики chapter/section/appendix принадлежат группе соседей.
Учитываются включённые нумеруемые узлы; префикс берётся от ближайшего
нумеруемого предка. Потомки приложения используют decimal; обозначения
приложений — латинские A…Z, AA… . Структурные номера 0.1 выводятся текстовыми
префиксами; numbering.xml относится только к обычным Markdown-спискам.
Каждая новая последовательность списка имеет собственные abstractNum/num,
уровни и startOverride. Вложенные списки сохраняют глубину и формат уровня.

В схеме 0.2 core.heading_numbering обходит все структурные и Markdown-
заголовки одной последовательностью. Block.heading_number содержит план:
уровень, путь, значения счётчиков и профили уровней. renderers.heading_numbering
превращает его в abstractNum/num без текстовых цифровых префиксов.
Стиль HeadingN сохраняет outlineLvl без numPr. Нумерация задаётся прямо
в абзацах через numId и ilvl; девять уровней abstractNum имеют явные отступы
и не связаны со стилями через pStyle. Профиль основан на файле пользователя,
пронумерованном Microsoft Word. Исключения профиля создают новые нативные
потоки с начальными значениями. Подробный контракт — NUMBERING.md.

## Оформление и рендеринг

`StyleResolver.overrides` накапливает только явные переопределения цепочки
based_on. `resolve` применяет глобальную базу, выбранный body, функциональный
стиль. Объект line_spacing заменяется целиком. Body наследуется по дереву;
heading-стиль остаётся локальным. Контекстные правила ячеек/списков и явная
семантика Markdown применяются последними.

Word получает реальные Heading 1…6, Title и вычисленные именованные стили.
Комбинация body/functional кешируется в отдельный стиль Word. Outline level
задаётся независимо от визуального имени стиля. Форматирование исходного
шаблона библиотеки очищается перед применением полного вычисленного профиля:
не должны проникать рамки Title, numPr Subtitle или theme-параметры.

Низкоуровневые функции OOXML выделены в `ooxml_extensions.py`: bookmarks,
hyperlinks, PAGE, numbering, геометрия и дополнительные свойства. Вставка
свойств учитывает порядок элементов WordprocessingML. Настройки шрифта
включают ascii/hAnsi/eastAsia/cs, язык и межсимвольный интервал.

Разрывы хранятся как отложенный boolean-запрос, применяемый к следующему
видимому блоку. Соседние запросы объединяются, первый и последний не создают
пустых страниц, after обрабатывается после потомков. Для таблицы на границе
страницы используется связанный с ней технический абзац.

## Ресурсы и выпуск

Изображения разрешаются от физического source с контролем корня. Pillow
проверяет двоичное содержимое. SVG разбирается defusedxml, активное содержимое
и внешние зависимости запрещены; CairoSVG получает локальные байты и
запрещающий любые загрузки url_fetcher. Сетевые вызовы и shell-команды в
движке отсутствуют. Кеш DLL Cairo живёт внутри процесса; установка не нужна.

Временный DOCX создаётся рядом с итоговым, проверяется и заменяет его только
после успеха. Проверка включает CRC, XML, обязательные части, внутренние OPC
relationships, уникальность/баланс закладок, цели hyperlinks, определения
стилей/numId и повторное открытие через публичный API python-docx. Модуль
diagnostics.numbering_graph дополнительно проверяет связи стилей, уровней и
определений, включая запрет style-level ilvl по MS-OI29500 2.1.50.
diagnostics.numbering_inspector рассчитывает метки уже после проверки графа.
Центральная CLI tools/verify_delivery использует эту же проверку и сравнивает
поставку с моделью входного проекта. Это не
полная XSD-проверка ECMA-376 и не движок вёрстки страниц.

BuildReport является общим результатом для CLI/GUI/API; аргументы командной
строки не входят в ядро. Следующий этап может добавить renderer для другого формата
и интеграционную визуальную проверку без изменения модели.

## Рабочая Studio

Frontend `studio/frontend/src` обращается к локальному FastAPI из
`studio/backend/md2doc_web`. Корень репозитория вычисляется по расположению
скриптов. Backend читает фактические YAML-ссылки из document.yaml, хранит
черновики/состояние в пределах текущего сеанса и создаёт изолированный снимок
для CLI и проверки доставки. Итог публикуется атомарно. Редакторы Markdown
и YAML проверяют внешний revision и сохраняют резервную копию перед записью.
Статический frontend обслуживается из `studio/frontend/build`, полученного
сборкой SvelteKit. Файлы `design/ui` в этом потоке не используются.
